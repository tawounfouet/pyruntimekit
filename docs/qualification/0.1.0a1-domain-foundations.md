# PyRuntimeKit 0.1.0a1 — Domain Foundations Qualification

## Status

**Candidate qualification report.**

This document becomes the release qualification record once the PR carrying these checks passes the complete CI gate and is merged to `main`.

## Scope

This qualification covers only the `0.1.0a1 — Domain Foundations` milestone:

- typed identifiers required by implemented domain concepts;
- Workload model;
- Run aggregate and snapshot/version contracts;
- Attempt model;
- Failure model;
- ExecutionResult / RunResult / ArtifactRef;
- Run domain events;
- Run lifecycle transition matrix;
- pure domain invariants;
- package/import/typing/architecture boundaries.

It does **not** qualify:

- RuntimeKernel;
- Runner/application services;
- executors;
- persistence;
- checkpoints;
- effects;
- workers;
- leases/fencing;
- distributed execution;
- observability transports.

Those belong to later milestones.

## Typed identifier scope clarification

The target architecture names future identifiers such as:

- `WorkerId`;
- `ExecutorId`;
- `EffectId`;
- `CheckpointId`;
- `LeaseId`.

Their owning concepts are not part of the implemented `0.1.0a1` domain slice. Creating those identifiers now would expand the milestone rather than qualify it.

The current milestone therefore qualifies the identifiers required by concepts that actually exist:

```text
Run               -> RunId
Workload          -> WorkloadId
Failure           -> FailureId
ArtifactRef       -> ArtifactId
DomainEvent       -> EventId
Attempt           -> RunId + AttemptNumber
```

Future identifier families are introduced when their owning domain model starts.

## Architecture boundary

The qualification suite parses every Python module in `src/pyruntimekit/domain/` and rejects imports of the infrastructure/runtime families forbidden by the repository architecture, including:

```text
asyncio
threading
multiprocessing
subprocess
SQL/database clients
Redis
Celery
Docker SDK
OpenTelemetry
PyAgentsKit
PyScheduleKit
```

It also rejects inward dependency inversions from Domain toward future higher layers such as:

```text
api
application
kernel
executors
stores
workers
coordination
observability
security
sandbox
```

## Lifecycle qualification

The canonical Run state machine contains 13 states.

The qualification suite evaluates every pair:

```text
13 current states
x
13 requested next states
=
169 transition combinations
```

For each pair:

- a transition listed in the normative matrix must be accepted;
- every other transition must raise `InvalidRunTransitionError`.

This proves in particular that terminal states cannot reopen.

## Deferred normative invariants

Some target invariants cannot yet be executable because their underlying domain concepts are intentionally absent from `0.1.0a1`:

- deadline immutability across retries;
- effect replay safety;
- lease ownership;
- fencing-token monotonicity;
- stale-worker effect rejection;
- full persisted transition/event atomicity.

These are **deferred**, not considered satisfied.

They must become executable qualification gates when their corresponding milestones introduce Deadline, Effect, Lease, Worker and persistence contracts.

## Release boundary

A successful qualification means:

> PyRuntimeKit `0.1.0a1` has a coherent, typed, infrastructure-independent and fully tested domain foundation.

It does **not** mean that PyRuntimeKit can execute workloads yet.

The next release slice, `0.1.0a2`, introduces the RuntimeKernel and the first executable vertical path.

## Final release statement

The expected `0.1.0a1` release statement is:

> PyRuntimeKit 0.1.0a1 introduces the domain foundation: Workload, Run, Attempt, Failure, Results, Domain Events and Run lifecycle invariants. No execution backend or persistence guarantee is included yet.
