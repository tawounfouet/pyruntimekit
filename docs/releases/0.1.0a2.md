# PyRuntimeKit 0.1.0a2 — Runtime Kernel

**First executable PyRuntimeKit vertical slice.**

PyRuntimeKit 0.1.0a2 introduces RuntimeKernel, ExecutionContext, SimpleRunner, InlineExecutor, Runtime.submit() and RunHandle, with normalized success/failure execution and explicit synchronous in-memory semantics.

## What is included

This second pre-alpha release turns the qualified domain foundation from `0.1.0a1` into a complete local execution path.

### Runtime lifecycle authority

`RuntimeKernel` is now the explicit authority for Run lifecycle evolution.

It owns:

- command interpretation;
- canonical transition validation;
- RunVersion progression;
- exact AttemptNumber progression when entering RUNNING;
- terminal-state protection;
- lifecycle DomainEvent creation;
- final RunResult evidence for SUCCEEDED/FAILED decisions.

The qualified success path is:

```text
version 0  CREATED    run.created
version 1  ADMITTED   run.admitted
version 2  QUEUED     run.queued
version 3  RUNNING    run.started
version 4  SUCCEEDED  run.succeeded
```

The qualified failure path ends instead with:

```text
version 4  FAILED     run.failed
```

### Execution context and orchestration

The release adds:

- immutable attempt-scoped `ExecutionContext`;
- `SimpleRunner` for one-attempt local orchestration;
- deterministic clock injection for Runtime/Runner/Executor tests;
- explicit separation between lifecycle authority and execution mechanism.

The central rule is:

```text
RuntimeKernel = lifecycle authority
Runner        = progression/orchestration
Executor      = execution mechanism
RunHandle     = client reference
```

### Executor contracts and InlineExecutor

The initial execution backend contracts include:

- `Executor`;
- `ExecutorDescriptor`;
- `ExecutorCapabilities`;
- `ResolvedWorkload`;
- `InlineExecutor`.

`InlineExecutor` truthfully declares only:

```text
IN_PROCESS
SHARED_MEMORY
TRUSTED_ONLY
```

It executes the resolved callable exactly once in the caller process/thread.

A plain callable return value becomes a successful `ExecutionResult`.

An ordinary Python `Exception` becomes a normalized Failure with:

```text
code     = EXECUTOR.INLINE.EXCEPTION
category = EXECUTION
origin   = EXECUTOR
scope    = ATTEMPT
```

The durable Failure stores a safe cause summary and does not persist a raw traceback.

### Public Runtime API

The first public execution API is now available:

```python
from pyruntimekit import Runtime
from pyruntimekit.domain import RunState

runtime = Runtime()

handle = runtime.submit(
    lambda context: {
        "run_id": context.run_id.value,
        "attempt": context.attempt.value,
    }
)

assert handle.status() is RunState.SUCCEEDED
print(handle.result().value)
```

`Runtime.submit()` accepts either:

- a synchronous Python callable following `callable(ExecutionContext) -> object`;
- an already-resolved `ResolvedWorkload`.

Callable adaptation creates an ephemeral `python.callable` Workload descriptor while keeping the live function outside the Domain model.

### RunHandle

`Runtime.submit()` returns a public `RunHandle[T]`.

The initial surface is:

```text
run_id
status()
result()
wait()
```

A RunHandle is a reference to execution, not ownership of a live Run.

For this synchronous release, a returned handle already references a terminal Run. Therefore `wait()` returns the existing terminal RunResult without polling or sleeping.

The bootstrap handle resolver is explicit:

```text
in-memory
process-local
ephemeral
non-durable
```

It is not a persistence Store.

The `0.1.0a2` qualification suite validates:

- successful Workload execution;
- failing Workload execution;
- invalid submission rejection;
- exact CREATED → ADMITTED → QUEUED → RUNNING → terminal progression;
- monotone RunVersion `0 → 4`;
- lifecycle DomainEvent type/version/timestamp coherence;
- Failure normalization;
- public Runtime.submit();
- RunHandle status/result/wait;
- multiple sequential Run isolation;

## Architecture guarantees

The release maintains the dependency direction:

```text
api → application → kernel → domain
```

Application may consume Executor contracts, but RuntimeKernel does not depend on concrete Executors and Executors do not own Run lifecycle semantics.

The Domain remains infrastructure-independent.

## Explicit non-goals

This release does not provide:

- AsyncExecutor;
- ThreadExecutor;
- ProcessExecutor or SubprocessExecutor;
- background execution;
- durable RunStore;
- SQLite/PostgreSQL persistence;
- cancellation request semantics;
- retry/recovery policy;
- checkpoints;
- effects/outbox;
- workers;
- heartbeats;
- leases/fencing;
- distributed coordination;
- observability transports;
- security sandboxing;
- PyAgentsKit/PyScheduleKit adapters.

These are deliberately deferred.
