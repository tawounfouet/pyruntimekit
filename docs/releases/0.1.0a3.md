# PyRuntimeKit 0.1.0a3 — Async & Thread Execution

**Qualified local concurrent execution.**

PyRuntimeKit 0.1.0a3 extends the local execution layer with AsyncExecutor and ThreadExecutor while preserving the RuntimeKernel lifecycle authority established in 0.1.0a2.

The release adds explicit context propagation, bounded local capacity, backpressure, standardized Executor conformance, normalized failures, truthful cancellation semantics and explicit thread-pool cleanup.

## What is included

### Executor contract evolution

The Executor model now distinguishes synchronous and asynchronous resolved workloads without breaking the existing synchronous Runtime path.

The milestone includes:

- the existing synchronous `Executor` contract;
- `ResolvedWorkload` for synchronous callables;
- `ResolvedAsyncWorkload` for awaitable callables;
- `AsyncExecutorContract`;
- `ThreadExecutorContract`;
- stable `ExecutorDescriptor` and `ExecutorCapabilities`.

The root public API remains intentionally unchanged:

```python
from pyruntimekit import Runtime, RunHandle
```

`Runtime.submit()` remains synchronous and continues to use the qualified InlineExecutor path.

### AsyncExecutor

`AsyncExecutor` executes an already-resolved asynchronous Workload in an explicit asyncio Task.

Its qualified guarantees are:

```text
same process
same thread
asyncio Task
shared memory
ContextVar propagation
ContextVar isolation
bounded active concurrency
ordinary exception normalization
CancelledError preserved as control flow
```

A successful async callable is normalized to `ExecutionResult.success(...)`.

An ordinary exception is normalized to a Failure with:

```text
code     = EXECUTOR.ASYNC.EXCEPTION
category = EXECUTION
origin   = EXECUTOR
scope    = ATTEMPT
```

The Failure stores a safe cause summary and does not persist a raw traceback reference.

### ThreadExecutor

`ThreadExecutor` offloads synchronous Workloads to an owned `ThreadPoolExecutor`.

Its qualified guarantees are:

```text
same process
different worker thread
shared memory
ContextVar propagation
bounded in-flight submission
ordinary exception normalization
explicit pool cleanup
```

The ThreadExecutor owns its pool and exposes explicit `close()` semantics.

A closed executor rejects new execution.

An ordinary thread workload exception is normalized to:

```text
code     = EXECUTOR.THREAD.EXCEPTION
category = EXECUTION
origin   = EXECUTOR
scope    = ATTEMPT
```

### Context propagation and isolation

Both concurrent backends explicitly propagate ambient ContextVars.

For AsyncExecutor:

```text
caller Context
      │
      ▼
copy_context()
      │
      ▼
explicit asyncio Task context
      │
      ▼
async Workload
```

Concurrent tasks receive isolated context copies.

For ThreadExecutor:

```text
caller Context
      │
      ▼
copy_context()
      │
      ▼
ThreadPool submission
      │
      ▼
worker thread
```

A reused worker thread does not retain context mutations from a previous Workload.

### Bounded local capacity and backpressure

The milestone introduces explicit local capacity limits.

AsyncExecutor uses:

```text
max_concurrency
      │
      ▼
asyncio.BoundedSemaphore
      │
      ▼
Task creation / execution
```

ThreadExecutor uses:

```text
max_in_flight
      │
      ▼
capacity gate
      │
      ▼
ThreadPoolExecutor submission
```

`max_in_flight` is independent from `max_workers`.

Excess work waits before entering the backend execution mechanism, preventing silent unbounded submission through the local Executor API.

Both executors expose their current local load.

### Cancellation semantics

The release deliberately avoids claiming stronger cancellation than Python can provide.

For AsyncExecutor:

```text
CancelledError
=
control-flow cancellation signal
```

It is not normalized into an ordinary Failure and the acquired capacity slot is released.

For ThreadExecutor:

```text
cancel asyncio await
!=
terminate running Python thread
```

If the awaiting Task is cancelled while the underlying thread continues, the ThreadExecutor keeps the capacity slot until the backend Future actually completes.

No hard thread cancellation guarantee is claimed.

## Conformance

A standardized Executor conformance matrix runs shared logical scenarios against:

- InlineExecutor;
- AsyncExecutor;
- ThreadExecutor.

The shared matrix verifies:

- successful execution;
- result normalization;
- preservation of an existing ExecutionResult;
- ordinary exception normalization;
- safe Failure payloads;
- exact ExecutionContext delivery;
- Workload/ExecutionContext identity validation;
- descriptor stability;
- capability consistency;
- preservation of the RuntimeKernel authority boundary.

Backend-specific tests additionally qualify:

- async Task identity and cancellation;
- thread execution identity;
- context propagation and isolation;
- bounded capacity;
- backpressure;
- resource cleanup.

## Architecture guarantees

The authority model remains:

```text
RuntimeKernel = Run lifecycle authority
Runner        = progression / orchestration
Executor      = execution mechanism
ExecutionContext = explicit attempt context
```

AsyncExecutor and ThreadExecutor do not depend on Runtime API, application orchestration or Kernel lifecycle implementation.

Kernel and application code do not bind directly to concrete concurrent executor modules.

## Explicit non-goals

This release does not provide:

- ProcessExecutor;
- SubprocessExecutor;
- timeout semantics;
- deadline semantics;
- hard thread cancellation;
- public AsyncRuntime;
- public ThreadRuntime;
- background public Runtime submission;
- durable RunStore;
- SQLite/PostgreSQL persistence;
- workers;
- heartbeats;
- retry/recovery runtime;
- checkpoints;
- effects/outbox;
- leases/fencing;
- distributed coordination;
- remote execution;
- sandboxing.

Those capabilities remain deliberately deferred.

## Release boundary

PyRuntimeKit 0.1.0a3 means:

> the project has a qualified local execution layer covering direct, asyncio Task and thread-backed execution mechanisms with explicit context and capacity semantics.

It does not mean that the public Runtime has become asynchronous, durable or distributed.
