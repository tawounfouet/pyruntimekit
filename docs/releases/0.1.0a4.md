# PyRuntimeKit 0.1.0a4 - Process & Subprocess Execution

**Qualified isolated execution for trusted Python workloads and explicit OS commands.**

PyRuntimeKit 0.1.0a4 extends the local execution mechanisms from 0.1.0a3 with
`ProcessExecutor` and `SubprocessExecutor`. It introduces explicit process
isolation, a Python-object serialization boundary, bounded admission,
observable load, dedicated failure normalization and defined cleanup semantics.

It **does not** turn the root `Runtime` API into a process runtime: 
`Runtime.submit()` continues to execute synchronously through
`InlineExecutor`.

## What is included

### Process/Subprocess contracts

- `ProcessExecutorContract` for resolved synchronous Python callables;
- `SubprocessExecutorContract` for resolved commands;
- immutable `SubprocessCommand(argv, cwd, env)`;
- `ResolvedSubprocessWorkload`;
- capability values `PROCESS_EXECUTION`, `SUBPROCESS_EXECUTION`,
  `PROCESS_ISOLATION` and `SERIALIZED_BOUNDARY`;
- backend-specific `ExecutorDescriptor` and truthful capability declarations.

The concrete executors are intentionally imported from their own modules:

```python
from pyruntimekit.executors.process import ProcessExecutor
from pyruntimekit.executors.subprocess import SubprocessExecutor
```

Neither class is re-exported by the package root or
`pyruntimekit.executors` contracts namespace.

### ProcessExecutor

`ProcessExecutor` owns a `concurrent.futures.ProcessPoolExecutor`.

It provides:

- execution in another Python process and address space;
- explicit `ResolvedWorkload + ExecutionContext` pickling preflight;
- explicit child result serialization and parent deserialization;
- preservation of a returned `ExecutionResult`;
- normalized ordinary Python callable failures;
- distinct input, output and decode serialization failures;
- `max_workers` and separate `max_in_flight` admission limits;
- observable `current_load`;
- explicit idempotent `close(wait=..., cancel_futures=...)`.

The standardized failure codes are:

```text
EXECUTOR.PROCESS.EXCEPTION
EXECUTOR.PROCESS.INPUT_SERIALIZATION
EXECUTOR.PROCESS.RESULT_SERIALIZATION
EXECUTOR.PROCESS.RESULT_DESERIALIZATION
```

The serialization format is Python stdlib `pickle` with
`pickle.HIGHEST_PROTOCOL`. This is a **trusted-only ephemeral boundary**,
not a safe deserializer for untrusted input or a cross-version network format.
Ordinary lambdas/local functions/closures are not guaranteed to be picklable.
A child process does not constitute a security sandbox.

### SubprocessExecutor

`SubprocessExecutor` launches one explicit OS command at a time per
admitted execution, up to `max_concurrency`.

It provides:

- `asyncio.create_subprocess_exec()` and literal argv semantics;
- no implicitly invoked shell;
- optional `cwd` and environment overlay;
- UTF-8 output decoding with replacement on malformed data;
- `stdout`, `stderr` and `exit_code` preservation;
- success on zero exit code;
- normalized non-zero exit and command launch errors;
- bounded `max_concurrency` and observable `current_load`;
- explicit idempotent `close()`, rejecting new commands.

The standardized failure codes are:

```text
EXECUTOR.SUBPROCESS.NONZERO_EXIT
EXECUTOR.SUBPROCESS.EXCEPTION
```

Subprocess execution does not transport Python return objects, so the backend
**does not declare** `SERIALIZED_BOUNDARY`.

### Capacity and cancellation

The backends have different ownership boundaries:

```text
ProcessExecutor:
  max_in_flight -> ProcessPoolExecutor.submit()
                -> backend Future completion -> slot release

SubprocessExecutor:
  max_concurrency -> OS command creation
                  -> completion/cancellation cleanup -> slot release
```

ProcessExecutor's `max_workers` limits concurrent process workers, whereas
`max_in_flight` limits all admitted Futures (running or queued).

Cancelling a caller's `await` on ProcessExecutor does not promise to kill a
running worker. Capacity remains assigned until the underlying Future is done.

SubprocessExecutor cancellation attempts to terminate its child, awaits cleanup
and re-raises `CancelledError`. This is a best-effort cleanup behavior, **not**
a hard process-cancellation guarantee. Calling `close()` does not terminate
commands already active.

### Capability truthfulness

| Capability | ProcessExecutor | SubprocessExecutor |
| --- | :---: | :---: |
| `TRUSTED_ONLY` | Yes | Yes |
| `PROCESS_ISOLATION` | Yes | Yes |
| `BOUNDED_CAPACITY` | Yes | Yes |
| `PROCESS_EXECUTION` | Yes | No |
| `SUBPROCESS_EXECUTION` | No | Yes |
| `SERIALIZED_BOUNDARY` | Yes | No |
| `IN_PROCESS` | No | No |
| `SHARED_MEMORY` | No | No |

No timeout, deadline, durable, remote or distributed capability is claimed.

## Architecture and compatibility

The existing authority model is preserved:

```text
RuntimeKernel     = Run lifecycle authority
Runner            = application orchestration
Executor          = execution mechanism
ExecutionContext  = attempt context
RunHandle         = public client reference
```

The root API is unchanged:

```python
from pyruntimekit import Runtime, RunHandle
```

`Runtime.submit()` remains synchronous and backed by `InlineExecutor`.
No public `ProcessRuntime` or `SubprocessRuntime` is introduced. Existing
Domain Foundations (a1), Runtime Kernel (a2), and Async/Thread (a3)
qualification suites continue to run.

## Explicit non-goals

This release does not introduce:

- public Runtime backend selection or asynchronous Runtime submission;
- hard process cancellation, guaranteed kill or process-group management;
- timeout/deadline policy or child crash recovery;
- plugin serialization, cloudpickle/dill or durable pickle payloads;
- remotely scheduled, durable or distributed execution;
- checkpoint/Store, worker ownership or leases/fencing;
- sandboxing of untrusted work;
- PyAgentsKit/PyAgentRuntime integrations.

## Release boundary

PyRuntimeKit 0.1.0a4 means that local direct, asyncio Task, thread,
Python process and explicit OS subprocess execution primitives are available
with qualified capability boundaries.

It does not imply public runtime process orchestration, security isolation,
remote scheduling, durability or distributed coordination.
